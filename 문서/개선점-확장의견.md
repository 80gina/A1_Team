# 개선점과 확장 의견 — 팔도 밥상 트렌드

| 항목 | 내용 |
|---|---|
| 작성 시점 | 과제 완료 직후 (2026-08-27) |
| 기준 데이터 | raw 158건 → clean 16건, 요약·감성 16건, 분석 3건 |
| 목적 | 측정된 한계를 적고, 다음에 무엇을 할지 정한다 |

> 이 문서는 "더 잘할 수 있었다"는 반성문이 아니다.
> **무엇이 얼마나 부족한지 숫자로 적고, 고치는 방법과 비용을 함께 적은 계획서**다.

---

## 1. 측정된 한계

### 1-1. 분류 정밀도 87.5% — 가장 큰 약점

**실측**

| 항목 | 값 |
|---|---|
| 정제 통과 | 16건 |
| 오분류 | **2건** |
| 정밀도 | **87.5%** |

**오분류 2건의 정체**

| 기사 | 잘못 들어간 곳 | 걸린 낱말 |
|---|---|---|
| 예술인 채용·기업 협업…'2026 예술 일자리 박람회' | 미식축제 | `박람회` + 본문의 음식 관련 낱말 |
| LG 오스틴, NC전서 구단 외인 첫 사이클링 히트…잠실구장 | 맛집·외식 | 본문의 `맛집` (구장 주변 맛집 언급 추정) |

**원인 분석**

키워드 매칭은 **낱말이 어디에 나왔는지**를 구분하지 못한다.
제목에 나온 `맛집` 과 본문 끄트머리에 스쳐 지나간 `맛집` 이 같은 무게를 갖는다.

이미 두 가지 보완을 넣었지만 충분하지 않았다.

| 넣은 조건 | 효과 | 한계 |
|---|---|---|
| `require_any` (함께 나와야 할 말) | '번개장터' 같은 명백한 오분류 차단 | 본문에 음식 낱말이 우연히 있으면 통과 |
| `exclude` (있으면 탈락) | 영화제·암표 등 차단 | 미리 아는 경우만 막을 수 있다 |

### 1-2. 정제 통과율 10.6% — 소스 선택의 문제

158건을 모아 16건만 남았다. 통과율 자체는 필터가 일한다는 뜻이라 문제가 아니지만,
**AI 호출 비용 대비 수확이 낮다**는 뜻이기도 하다.

| | 현재 |
|---|---|
| 수집 요청 | RSS 3회 + 크롤링 39회 = **42회** |
| 최종 활용 | **16건** |
| 소스 | 경향신문 종합·문화·라이프 (음식·여행 전문 아님) |

### 1-3. 단일 소스 의존

경향신문 하나만 쓴다. 제약사항이 허용하는 범위이지만 두 가지 위험이 있다.

| 위험 | 결과 |
|---|---|
| 그 사이트가 개편되면 | `div.art_body` 선택자가 깨져 본문 수집이 멈춘다 |
| 한 언론사의 시각만 반영 | 트렌드 분석이 편향될 수 있다 |

### 1-4. 데이터 규모

기사 16건, 기간 19일(08-08~08-26)로 "트렌드"를 말하기에는 표본이 얇다.
감성 분포(긍정 9 / 중립 5 / 부정 2)도 2건 차이가 비율을 크게 흔든다.

### 1-5. 감성 판정의 검증 부재

감성은 AI 판정만 있고 **사람이 확인한 정답이 없다.** 정확도를 알 수 없다.
분류 정밀도는 눈으로 세었지만 감성은 그러지 못했다.

## 2. 개선 방안 — 비용과 효과

### 2-1. [최우선] 분류를 AI에게 맡긴다

**방법** — 2단계 구조로 바꾼다.

```
현재:  키워드 매칭 → 카테고리 확정
개선:  키워드 매칭(1차 거르기) → AI 분류(최종 판정)
```

키워드로 158건 → 30건 정도로 좁힌 뒤, **그 30건만 AI에게** 카테고리를 묻는다.

| 항목 | 값 |
|---|---|
| 추가 AI 호출 | 약 30회 (기존 16회 요약 + 16회 감성에 더해) |
| 추가 비용 | Flash-Lite 기준 미미 |
| 기대 효과 | 정밀도 87.5% → 95% 이상 |
| 구현 난이도 | **낮음** — `enum` 스키마 호출은 감성 분석에서 이미 검증됨 |

**구현 스케치**

> 📄 설계안 — 실행하지 마세요
> ```
> CATEGORY_SCHEMA = {
>   "type": "object",
>   "properties": {
>     "category": {"type": "string",
>                  "enum": ["향토음식","맛집·외식","식재료·제철","미식축제","여행·관광","해당없음"]},
>     "confidence": {"type": "number"},
>     "reason": {"type": "string"}
>   },
>   "required": ["category", "confidence", "reason"]
> }
> ```

`confidence` 를 함께 받으면 **애매한 건만 사람이 확인**하는 흐름도 만들 수 있다.

**중요한 점** — 키워드 단계를 없애지 않는다. 158건 전부를 AI에 보내면
호출이 10배로 늘어난다. **싼 필터로 먼저 좁히고, 비싼 판단을 나중에** 하는 순서를 지킨다.

### 2-2. [높음] 낱말의 위치에 가중치를 준다

AI 분류로 가기 전, 키워드 방식만으로도 개선 여지가 있다.

| 위치 | 가중치 | 근거 |
|---|---|---|
| 제목 | 3 | 기사의 주제를 담는다 |
| 요약(description) | 2 | 핵심 내용 |
| 본문 | 1 | 스쳐 지나가는 언급이 섞인다 |

합산 점수가 기준을 넘을 때만 분류한다.
야구 기사의 본문 끝에 나온 `맛집` 은 1점이라 통과하지 못한다.

| 항목 | 값 |
|---|---|
| 추가 비용 | **0원** (AI 호출 없음) |
| 구현 난이도 | 낮음 — `cleaner.classify()` 한 함수만 수정 |
| 기대 효과 | 정밀도 87.5% → 92% 내외 추정 |

### 2-3. [높음] 소스를 늘린다

`config.json` 의 `sources` 배열에 항목을 추가하면 코드 수정 없이 늘어난다.
다만 언론사마다 본문 선택자가 다르므로 `crawl.selectors` 도 함께 늘려야 한다.

**후보**

| 소스 | 성격 | 기대 |
|---|---|---|
| 다른 종합지 RSS (한겨레·경향 외) | 표본 확대 | 통과율은 비슷, 절대 건수 증가 |
| 한국관광공사 보도자료 | 여행·축제 전문 | **통과율 크게 상승** |
| 농림축산식품부 보도자료 | 식재료·제철 전문 | 카테고리 균형 개선 |
| 지자체 문화관광 페이지 | 지역 축제 | 미식축제 카테고리 보강 |

현재 카테고리가 여행·관광 10 : 나머지 6 으로 기울어 있는데,
음식 전문 소스를 넣으면 균형이 맞는다.

**선택자 문제를 줄이는 방법** — 소스별 선택자를 `config.json` 에 함께 둔다.

> 📄 설계안 — 실행하지 마세요
> ```
> {"name":"kwt", "url":"...", "selectors":["div.article_body","#contents"]}
> ```

현재는 선택자가 전역 하나뿐이라, 소스가 늘면 이 구조부터 바꿔야 한다.

### 2-4. [중간] 감성 판정에 검증 표본을 만든다

16건 중 **10건을 직접 읽고 정답을 매긴 뒤**, AI 판정과 비교한다.
일치율을 재면 감성 기능의 신뢰도를 숫자로 말할 수 있다.

| 항목 | 값 |
|---|---|
| 비용 | 시간 30분 |
| 효과 | "감성 정확도 ○○%" 라고 말할 수 있게 된다 |

측정하지 않은 기능은 자랑할 수 없다. 분류 정밀도를 실측한 것과 같은 이유다.

### 2-5. [중간] 수집 기간을 늘린다

RSS는 최근 50건까지만 준다. 매일 `daily.ps1` 이 돌면
**중복은 자동으로 걸러지면서 데이터가 누적**된다.

| 기간 | 예상 clean 건수 |
|---|---|
| 현재 (19일치, 1회 수집) | 16건 |
| 매일 수집 30일 | 60~100건 |
| 매일 수집 90일 | 200건 이상 |

**추가 구현 없이 스케줄만 걸면 된다.** 이미 만들어 둔 `daily.ps1` 이 그 역할이다.
200건이 쌓이면 "월별 추이", "계절별 키워드 변화" 같은 분석이 가능해진다.

### 2-6. [낮음] 선택자 깨짐을 감지한다

현재는 2단계 대체 경로로 넘어가도 **조용히 계속 진행**한다.
1단계 실패가 일정 비율을 넘으면 경고를 띄우도록 하면 좋다.

> 📄 설계안 — 실행하지 마세요
> ```
> if fallback_count / total > 0.3:
>     log.warning("선택자가 %d%% 빗나갔습니다. config.json 의 crawl.selectors 를 확인하세요.", ...)
> ```

스케줄로 자동 실행할 때는 **아무도 안 보고 있기 때문에** 이런 자가 진단이 중요하다.

## 3. 개선 우선순위

| 순위 | 항목 | 비용 | 효과 | 근거 |
|---|---|---|---|---|
| 1 | **AI 분류로 전환** | AI 호출 +30회 | 정밀도 87.5% → 95%+ | 가장 큰 약점을 직접 해결 |
| 2 | **위치 가중치** | 0원, 함수 1개 | 정밀도 → 92% 내외 | 비용 대비 효과가 가장 좋다 |
| 3 | **음식 전문 소스 추가** | 선택자 조사 시간 | 통과율·카테고리 균형 개선 | 표본 문제의 근본 해결 |
| 4 | **매일 수집 스케줄 가동** | 0원 (이미 구현됨) | 90일 후 200건 이상 | 시간이 대신 일해준다 |
| 5 | 감성 검증 표본 | 30분 | 신뢰도를 숫자로 | 측정하지 않으면 말할 수 없다 |
| 6 | 선택자 깨짐 감지 | 코드 몇 줄 | 무인 운영 안정성 | 스케줄 실행 시 필요 |

**2번을 먼저 하고 1번을 하는 것**이 순서상 낫다.
싼 개선으로 얼마나 좋아지는지 재고, 그래도 부족한 만큼만 AI에 맡기는 편이
비용과 효과를 함께 볼 수 있다.

## 4. 확장 방향 — 이 프로그램이 갈 수 있는 곳

### 4-1. 「팔도 밥상 캘린더」 — 제철·계절 축

지금은 "이번 달 무엇이 뜨는가"만 본다.
**1년치를 모으면 "몇 월에 무엇이 뜨는가"** 를 말할 수 있다.

| 필요한 것 | 이미 있는 것 |
|---|---|
| 1년치 데이터 | `daily.ps1` 스케줄 |
| 월별 집계 | `GROUP BY strftime('%m', published_date)` 한 줄 |
| 계절 차트 | `reporter.py` 에 함수 하나 추가 |

**"9월에는 전어, 10월에는 대하"** 같은 결과가 나온다.
콘텐츠 기획에서 가장 필요한 형태다.

### 4-2. 지역 축 추가 — 「어느 지역이 뜨는가」

현재 카테고리는 **무엇**(음식 종류)만 본다. **어디**가 빠져 있다.

기사에서 지역명(17개 시·도 + 주요 시군)을 뽑아 `region` 열을 추가하면
"이번 달 여수·울산이 많이 언급됐다" 같은 분석이 가능해진다.

| 방법 | 난이도 |
|---|---|
| 지역명 사전 매칭 | 낮음 — 카테고리 분류와 같은 구조 |
| AI에게 함께 묻기 | 낮음 — 분류 스키마에 `region` 필드 추가 |

지역 × 음식 2축이 되면 **히트맵**을 그릴 수 있고,
A1-02의 여행지 추천과 데이터를 주고받을 수 있다.

### 4-3. 레시피 파이프라인과의 실제 연결

지금은 `recipe_ideas` 가 **텍스트 제안**에서 멈춘다.
이걸 A1-01의 프롬프트 관리자에 **자동으로 등록**하면 흐름이 완결된다.

```
뉴스 수집 → 분석 → 레시피 소재 3건
                        ↓
        레시피 프롬프트 관리자에 프롬프트로 등록
                        ↓
        「순자 할머니」 페르소나로 레시피 생성
```

| 필요한 것 | 방법 |
|---|---|
| 소재 → 프롬프트 변환 | 템플릿 문자열 한 개 |
| 관리자에 전달 | JSON 파일로 내보내고 관리자가 읽기 |

**세 과제가 실제로 데이터를 주고받는 하나의 시스템**이 된다.
이 확장이 이 주제를 고른 이유를 완성한다.

### 4-4. 알림 — 무인 운영의 마지막 조각

스케줄로 매일 돌리면 아무도 결과를 안 본다.
조건에 걸릴 때만 알려주면 실제로 쓰이는 도구가 된다.

| 조건 | 알림 |
|---|---|
| 새 기사가 N건 이상 | "오늘 향토음식 기사 5건" |
| 특정 키워드 등장 | "'전어' 기사가 처음 나왔습니다" |
| 파이프라인 실패 | "수집 실패 — 선택자 확인 필요" |

메일이나 메신저 연동은 이 과제 범위 밖이지만,
`report` 결과를 파일로 남기는 구조가 이미 있어 붙이기 쉽다.

### 4-5. 웹 대시보드 — 이번엔 하지 않은 것

제약사항이 웹 UI를 금지했다. 다만 데이터 구조는 이미 준비되어 있다.

| 이미 있는 것 | 웹으로 갈 때 |
|---|---|
| SQLite 3테이블 | 그대로 읽으면 된다 |
| `export --format jsonl` | 프론트엔드가 바로 소비 가능 |
| 집계 함수들 | API 응답으로 재사용 |

`reporter.py` 를 건드리지 않고 새 모듈만 추가하면 된다.
**모듈을 7개로 나눈 값어치가 여기서 나온다.**

## 5. 이번 과제에서 배운 것 — 다음에 가져갈 원칙

| # | 원칙 | 어디서 배웠나 |
|---|---|---|
| 1 | **원본을 남겨두면 실수를 싸게 고칠 수 있다** | 번개장터 오분류 → 재수집 0회로 해결 |
| 2 | **품질을 숫자로 재지 않으면 문제를 못 본다** | 203자 요약. 프로그램은 정상 동작 중이었다 |
| 3 | **오류는 종류별로 다르게 다뤄야 한다** | 4xx 즉시 포기 / 5xx 재시도 / 404만 모델 전환 |
| 4 | **싼 필터로 좁히고 비싼 판단을 나중에** | 키워드로 158→16, AI는 16건에만 |
| 5 | **요청을 줄이는 것이 지연을 두는 것보다 근본적이다** | `--target clean` 으로 158→39 |
| 6 | **형식이 용도를 결정한다** | 자유형식 / JSON스키마 / enum — 집계 가능성이 형식을 정했다 |
| 7 | **한계를 측정해서 적는 편이 강하다** | 정밀도 87.5%를 감추지 않고 README에 적었다 |
