## 1. API/RSS 방식과 크롤링 방식의 장단점을 비교하여 설명할 수 있다

### 두 방식을 모두 구현했다

| | 방법 1 — RSS | 방법 2 — 크롤링 |
|---|---|---|
| 대상 | 경향신문 RSS 3종 (life / culture / total) | 각 기사 상세 페이지 |
| 도구 | `xml.etree.ElementTree` | `BeautifulSoup` |
| 얻는 것 | 제목, 요약(약 200자), 링크, 날짜, 카테고리 | **본문 전체** |
| 실측 | 소스당 50건씩 158건 확보 | 39건, 평균 1,681자 |

### 장단점 — 실측으로 확인한 것

| 항목 | RSS | 크롤링 |
|---|---|---|
| **안정성** | 형식이 정해져 있어 깨질 일이 적다 | 사이트 디자인이 바뀌면 코드가 바로 깨진다 |
| **서버 부담** | 목록 파일 1회 요청으로 50건 | 기사마다 1회 요청 (39건 = 39회) |
| **속도** | 3회 요청으로 158건 | 1초 지연 포함 39초 |
| **정보량** | 제목·요약뿐 (약 200자) | 본문 전체 (629~4,473자) |
| **정책** | 언론사가 공개할 의도로 제공 | robots.txt 확인과 예절이 필요 |

### 왜 둘 다 필요했나 — 실제 사건

처음에는 크롤링을 5건만 하고 요약을 돌렸다. 그랬더니 이런 로그가 나왔다.

```
[7/16] ID=10 요약 완료 (203자 → 148자)
[8/16] ID=11 요약 완료 (203자 → 124자)
```

**203자는 RSS 요약문의 길이**였다. 본문이 없어 결측값 처리 규칙에 따라
요약문을 본문 대신 쓴 것이다. 203자를 다시 요약해봐야 의미가 없다.

크롤링으로 본문을 채운 뒤에는 이렇게 바뀌었다.

```
[1/16] ID=1  요약 완료 (4339자 → 153자)
[5/16] ID=7  요약 완료 (2497자 → 182자)
```

**"RSS는 목록을, 크롤링은 내용을"** — 이것이 두 방식을 병행한 이유다.

### 크롤링 예절 (제약사항 7)

| 지킨 것 | 구현 |
|---|---|
| 사이트 정책 준수 | `robots.txt` 사전 확인 — 경향신문은 `User-agent: *` 에 대해 허용 |
| 요청 간 지연 | `config.json` 의 `request.delay_sec` (기본 1초) |
| 신원 명시 | User-Agent 에 프로젝트명·연락처 |
| 과도한 요청 금지 | `--limit` 으로 건수 제한 |
| **요청 자체를 줄임** | `--target clean` — 정제를 통과한 기사만 크롤링 |

마지막 항목이 가장 강한 조치다. 지연을 두는 것보다 **요청 수를 줄이는 것**이 근본적이다.
전체 158건 중 39건만 방문했다(25.8%).

### 본문 추출이 깨지지 않게 한 장치

| 단계 | 방법 | 실제 |
|---|---|---|
| 1 | `config.json` 의 선택자 순서대로 시도 | **39건 전부 1단계 성공** (`div.art_body`) |
| 2 | 실패 시 `<p>` 글자수 최다 영역을 본문으로 추정 | 사용되지 않음 (대비용) |

어느 경로로 찾았는지 로그에 남긴다. 1단계가 계속 실패하면 선택자를 고쳐야 한다는 신호다.

> 📸 `06_fetch.png` `08_crawl.png` `14_resummarize.png`

### 📋 요약

| 질문 | 답 |
|---|---|
| 두 방식의 핵심 차이는? | RSS는 **목록**(제목·요약 200자), 크롤링은 **내용**(본문 1,681자 평균) |
| RSS만으로 안 되는 이유는? | AI 요약의 재료가 200자면 요약이 성립하지 않는다 |
| 크롤링의 약점은? | 사이트 디자인 변경에 취약 → 2단계 대체 경로로 대비 |
| 예절은 어떻게 지켰나? | robots.txt 확인, 1초 지연, User-Agent 명시, `--target clean` 으로 요청 수 자체를 축소 |

## 2. 외부 API에서 데이터를 수집하고, 오류 상황을 처리하는 방법을 설명할 수 있다

### 원칙 — 오류를 종류별로 다르게 다룬다

`except Exception:` 하나로 뭉뚱그리면 이 구분이 사라진다.

| 상황 | 판단 | 동작 | 근거 |
|---|---|---|---|
| **4xx** (400·403·404) | 내 잘못 — 주소·키가 틀림 | **즉시 포기** | 재시도해도 결과가 같다 |
| **5xx** (500·503) | 저쪽 사정 — 서버 혼잡 | 2초 → 4초 → 8초 재시도 | 기다리면 풀린다 |
| **타임아웃** | 저쪽 사정과 동일 | 5xx와 같게 취급 | — |
| **429** (사용량 제한) | 속도 문제 | 4초 → 8초 → 16초 (더 길게) | 짧게 재시도하면 악화된다 |
| **AI 404** | 그 계정에서 못 쓰는 모델 | **다음 모델로 전환** | 모델을 바꾸면 해결된다 |

지수 백오프(대기를 2배씩 늘림)를 쓰는 이유는, 서버가 붐빌 때
모두가 짧은 간격으로 재시도하면 상황이 더 나빠지기 때문이다.

### 실제로 재시도가 작동한 기록

AI 요약 중 실제 타임아웃이 발생했고, 재시도로 살아났다.

```
[WARNING] AI 연결 실패 (1/3): ReadTimeout. 2초 뒤 재시도합니다.
[INFO] [13/16] ID=19 요약 완료 (1534자 → 212자)
...
[INFO] 요약 완료: 16건 성공, 0건 실패
```

**최종 결과는 0건 실패다.** 오류 처리가 없었다면 1건을 잃었다.

수집 단계에서도 검증했다(개발 환경의 프록시 차단을 이용).

```
[WARNING] 연결 실패 (1/3): ProxyError. 2초 뒤 재시도합니다.
[WARNING] 연결 실패 (2/3): ProxyError. 4초 뒤 재시도합니다.
[WARNING] 연결 실패 (3/3): ProxyError. 8초 뒤 재시도합니다.
[ERROR] khan_life 수집 실패: 3회 시도했지만 가져오지 못했습니다
[INFO] [RSS] khan_culture 수집 중...        ← 다음 소스로 계속 진행
```

**한 소스가 죽어도 다음 소스로 넘어간다.** 기사 하나가 실패해도 다음 기사로 넘어간다.

### 서버가 준 설명을 버리지 않는다

A1-02에서 403 오류의 응답 본문을 버려 원인을 찾지 못했던 경험이 있다.
이번에는 처음부터 본문을 오류 메시지에 실었다.

```
AI 요청이 거부되었습니다 (HTTP 400): {"error":{"message":"API key not valid"}}
```

"인증 실패"라고만 적었다면 키 문제인지 권한 문제인지 알 수 없다.

### API 키 관리 (제약사항)

| 항목 | 구현 |
|---|---|
| 코드에 직접 작성 금지 | `.env` 파일 + `python-dotenv` |
| 저장소 유출 방지 | `.gitignore` 에 `.env` 등록 — **추적 파일 0건 확인** |
| 로그 노출 방지 | `config.mask()` — 앞 4자만 남기고 가림 |

```
[INFO] Gemini 키 확인: AQ.A******** / 모델: gemini-3.5-flash-lite
```

### 모델 이름을 코드에 박지 않는다

A1-02에서 AI가 짐작한 모델명이 404를 냈던 경험 때문에,
모델을 **목록**으로 두고 404일 때만 다음으로 넘어가게 했다.

```json
"model": "gemini-3.5-flash-lite",
"fallback_models": ["gemini-3.1-flash-lite"]
```

전환 조건을 404로 좁힌 것이 핵심이다. 400(키 오류)에서 모델을 바꾸면
같은 실패를 두 번 하게 된다.

> 📸 `12_summarize.png` `14_resummarize.png`

### 📋 요약

| 질문 | 답 |
|---|---|
| 4xx와 5xx를 왜 다르게 다루나? | 4xx는 내 잘못이라 재시도해도 같고, 5xx는 저쪽 사정이라 기다리면 풀린다 |
| 지수 백오프를 쓰는 이유는? | 짧은 간격 재시도가 몰리면 서버 상황이 더 나빠진다 |
| 실제로 효과가 있었나? | ReadTimeout 1건이 재시도로 살아나 **16건 성공 0건 실패** |
| 키는 어떻게 보호했나? | `.env` + `.gitignore`(추적 0건) + 로그 마스킹(`AQ.A********`) |
| 한 건이 실패하면? | 로깅 후 스킵하고 다음으로 진행 — 프로그램은 끝까지 돈다 |

## 3. raw 데이터와 clean 데이터를 분리 저장해야 하는 이유와 각 단계의 역할을 설명할 수 있다

### 두 저장소의 역할

| | `raw_news` | `clean_news` |
|---|---|---|
| 담기는 것 | 받은 그대로, 손대지 않음 | 검증·정규화를 거친 정제본 |
| 건수 | 158건 | 16건 |
| 날짜 | `Tue, 26 Aug 2026 16:07:00 +0900` (원본 문자열) | `2026-08-26` (통일) |
| 제목 | `남해안 <b>전어</b> 축제&nbsp;개막` | `남해안 전어 축제 개막` |
| 함께 저장 | 수집 시각, 소스명, 수집 방법 (요건 2) | 카테고리, 분류 근거, 본문 출처 |

### 정제 5규칙 (요건 3)

| # | 규칙 | 구현 | 실측 |
|---|---|---|---|
| 1 | 필수 필드 검증 | url·제목·날짜 중 하나라도 없으면 제외 | — |
| 2 | 텍스트 정규화 | HTML 태그·`&nbsp;`·중복 공백 제거 | — |
| 3 | 날짜 형식 통일 | ISO 8601 / RFC 2822 / `YYYY.MM.DD` → `YYYY-MM-DD` | — |
| 4 | 결측값 처리 | 본문 없으면 요약문 사용 + 출처 기록 | 1건 제외(둘 다 없음) |
| 5 | 주제 분류 | 5개 카테고리 키워드 매칭, 미해당 제외 | 134건 제외 |

날짜 형식 통일이 필요했던 실제 이유: **같은 피드 안에서 두 형식이 섞여 있었다.**

```
2026-08-26T16:50:00+09:00        ← dc:date  (ISO 8601)
Tue, 26 Aug 2026 16:07:00 +0900  ← pubDate  (RFC 2822)
```

경향신문 RSS는 보통의 `pubDate` 가 아니라 `dc:date` 를 쓰는 항목이 섞여 있다.
raw에는 **원본 그대로** 담고, 통일은 정제 단계에서 한다.

### 중복 처리 정책 (요건 3)

| 정책 | 동작 | 언제 쓰나 |
|---|---|---|
| `skip` (기본) | 이미 있으면 그대로 둠 | 평소 운영 — 빠르다 |
| `upsert` | 새 내용으로 덮어씀 | **정제 규칙을 고친 뒤 전체 반영** |

중복 판별은 파이썬 반복문이 아니라 **DB에 맡겼다.**
`url TEXT NOT NULL UNIQUE` + `INSERT OR IGNORE` 로,
기존 158건과 일일이 비교하지 않는다.

실제 동작 확인:
```
1회차: 30건 저장, 0건 중복 건너뜀
2회차: 0건 저장, 30건 중복 건너뜀      ← 같은 기사를 두 번 넣지 않는다
```

### 분리 저장이 실제로 값을 한 순간

**사건** — 중고거래 플랫폼 '번개장터' 기사가 `장터` 키워드 때문에 미식축제로 분류되었다.

```
[ID=3] 미식축제 | 걸린 키워드: 장터
제목: 추석 승차권 암표 뿌리뽑는다
```

**대응** — raw 158건이 원본 그대로 남아 있었으므로,
**규칙만 고치고 정제만 다시** 돌렸다. 뉴스 사이트 재요청은 0회.

이를 위해 `clean --rebuild` 를 만들었다.
규칙에 더는 맞지 않는 기사를 clean에서 제거하되,
**살아남은 기사의 AI 요약문은 지우지 않는다** — API를 다시 부르지 않기 위해.

```
[INFO] 재구축: 규칙에 맞지 않게 된 6건을 clean 에서 제거했습니다.
[INFO] 정제 완료: 3건 저장, 13건 갱신, 135건 제외
```

6건이 빠지고, 새 규칙으로 3건이 새로 들어왔다.

**raw를 남기지 않았다면** 158건을 다시 수집해야 했고,
그 사이 내려간 기사는 영영 되찾을 수 없었다.

### 제외 사유를 집계한다

"그냥 135건 버림"이 아니라 왜 버렸는지가 남는다.

```
제외 사유 - 주제 밖(음식·여행 아님): 134건
제외 사유 - 본문·요약 모두 없음: 1건
```

이 집계가 곧 리포트의 **품질 지표**가 된다(요건 7).

> 📸 `07_dedup.png` `11_clean.png` `13_rebuild.png`

### 📋 요약

| 질문 | 답 |
|---|---|
| 왜 두 번 저장하나? | 정제 규칙이 틀렸을 때 **재수집 없이** 정제만 다시 돌리기 위해 |
| 실제로 그런 일이 있었나? | '번개장터' 오분류 → 규칙 수정 + `--rebuild` 로 6건 정리, 재요청 0회 |
| raw에 꼭 함께 담은 것은? | 수집 시각·소스명·수집 방법 (요건 2) |
| 날짜를 왜 통일하나? | 같은 피드에 `dc:date`(ISO)와 `pubDate`(RFC2822)가 섞여 있었다 |
| 중복은 어떻게 막나? | `url UNIQUE` + `INSERT OR IGNORE` — DB에 맡긴다 |
| skip과 upsert의 차이는? | skip은 평소 운영(빠름), upsert는 규칙 변경 후 전체 반영 |

## 4. AI API를 호출하여 텍스트를 요약하거나 분석하는 흐름을 설명할 수 있다

### 호출 흐름

```
clean_news에서 대상 선택
        ↓
프롬프트 조립 (제목 + 본문, max_input_chars로 잘라냄)
        ↓
POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
        ↓
응답 구조에서 텍스트 추출 → candidates[0].content.parts[*].text
        ↓
DB에 저장 (summary / sentiment / analyses)
```

### 같은 API를 세 가지 방식으로 부른다

**"무엇을 시키느냐"보다 "어떤 형태로 받느냐"가 파이프라인의 성립을 결정한다.**

| 용도 | 응답 형식 | 이유 |
|---|---|---|
| **요약** | 자유 형식 문장 | 사람이 읽을 글. 틀을 씌우면 문장이 딱딱해진다 |
| **인사이트** | JSON 스키마 강제 | 키워드·트렌드를 **프로그램이 꺼내** 리포트에 써야 한다 |
| **감성** | JSON + `enum` 제약 | `긍정`/`중립`/`부정` 셋 중 하나여야 **집계가 된다** |

자유 형식으로 "트렌드 분석해줘"라고 하면 이런 답이 온다.

```
안녕하세요! 분석해보니 가을 제철 식재료 기사가 눈에 띄네요. 그리고...
```

사람은 읽을 수 있지만 **프로그램은 "키워드 5개"만 꺼낼 수 없다.**
그래서 요청에 응답 구조를 함께 보낸다.

```
요청에 실려 간 것: responseMimeType=application/json
필수 키: ['trends','keywords','comparison','implications','recipe_ideas']
```

감성은 `enum` 이 없으면 "약간 긍정적입니다" 같은 답이 와서 집계가 깨진다.

### 인사이트 분석 항목 (요건 5 — 2개 이상 → 5개)

| 항목 | 내용 | 요건 대응 |
|---|---|---|
| `trends` | 주요 트렌드 3~5개 | ✅ 주요 트렌드 |
| `keywords` | 핵심 키워드 5~8개 (명사만) | ✅ 핵심 키워드 |
| `comparison` | 카테고리 간 공통점·차이점 | ✅ 공통점/차이점 |
| `implications` | 시사점 | ✅ 시사점 |
| `recipe_ideas` | **뉴스에서 얻는 레시피 소재 3개** | 이전 과제와의 연결 |

실제 산출 결과(2026-08-08 ~ 08-26, 16건 종합):

```
[주요 트렌드]
 - 추석 연휴와 단기 휴가를 맞아 국내외 단거리 여행지 및 지역 도시로의 이동이 급증하고 있다.
 - 지역 문화유산과 특산물을 활용한 관광 상품 및 디퓨저 등 이색적인 로컬 기념품 개발이 활발하다.
 - 해외 인플루언서들을 통한 뭉티기, 번데기 등 도전적인 K-로컬 푸드 미식 여행 홍보가 주목받고 있다.

[핵심 키워드]
 여수섬박람회, 역사여행, 아기판다, 관광기념품, 추석연휴, K푸드, 지역균형발전, 잠실구장

[레시피 소재 제안]
 - 한우 뭉티기 트리오 소스 플래터
 - 여수 섬 밥상 해산물 솥밥과 제철 나물 무침
```

**AI가 실제 기사에서 근거를 찾아 레시피 소재를 도출했다.**
'여수섬박람회'와 'K-로컬 푸드 헌터스' 기사가 재료가 되었다.

### 요약 대상 선택과 실패 처리 (요건 4)

| 옵션 | 동작 |
|---|---|
| `--unsummarized` (기본) | 아직 요약이 없는 것만 |
| `--all` | 전체 재요약 |
| `--id N` | 특정 한 건 |

이미 요약된 기사는 **기본 스킵**이다.

```
요약 대상(unsummarized): [1, 2]
1건 요약 후 대상: [2]        ← 이미 된 건 자동 제외
```

API 실패 시에는 **로깅 후 스킵하고 다음 기사로** 넘어간다.
20건 중 3건이 실패해도 17건은 요약된다.

### 응답을 신뢰하지 않는 방어층

`responseSchema` 를 걸어도 코드블록이 섞여 오는 경우가 드물게 있다.
그래서 파싱 전에 한 번 걷어낸다.

**AI가 만든 규칙을 AI가 못 지킬 수 있다**는 전제로 짠 코드다.

### 분석 결과는 별도 저장한다 (요건 5)

`analyses` 테이블에 기간·카테고리·건수·모델명과 함께 저장한다.
`analyze --show` 로 **API 호출 없이** 다시 꺼내 볼 수 있고, 리포트가 이를 인용한다.

> 📸 `12_summarize.png` `15_analyze.png` `16_analyze_show.png` `22_sentiment.png`

## 5. 수집된 데이터를 집계하고 matplotlib으로 시각화하는 과정을 설명할 수 있다

### 집계 → 시각화 흐름

```
SQL 집계                          matplotlib                 PNG
──────────────────────────────────────────────────────────────────
GROUP BY category         →  가로 막대   →  chart_category.png
GROUP BY published_date   →  꺾은선      →  chart_daily.png
GROUP BY sentiment        →  세로 막대   →  chart_sentiment.png   (보너스)
```

집계는 파이썬 반복문이 아니라 **SQL의 `GROUP BY`** 에 맡겼다.
DB가 인덱스를 쓰기 때문에 건수가 늘어도 느려지지 않는다.

### 한글 폰트 — 이 단계의 함정

matplotlib 기본 폰트에는 **한글 글자가 없다.** 그대로 그리면 제목이 `□□□□` 로 나온다.

| 조치 | 내용 |
|---|---|
| 폰트 탐색 | `Malgun Gothic` → `AppleGothic` → `NanumGothic` → `Noto Sans CJK` → `Gulim` 순으로 설치된 것을 찾아 지정 |
| 마이너스 기호 | `axes.unicode_minus = False` — 없으면 음수 눈금의 `−` 가 또 깨진다 |
| 실패 시 | 경고를 남기고 계속 진행 (프로그램을 멈추지 않는다) |

실행 결과:
```
[INFO] 한글 폰트 적용: Malgun Gothic
```

**파일이 만들어졌다는 것만으로는 확인이 안 된다.** 반드시 열어서 눈으로 봐야 한다.

### 차트를 읽기 쉽게 만든 결정

| 결정 | 이유 |
|---|---|
| 카테고리는 **가로** 막대 | `식재료·제철` 같은 긴 이름이 세로 막대에선 기울거나 겹친다 |
| 값을 막대 끝에 직접 표기 | 축 눈금을 되짚어 읽지 않아도 된다 |
| 추이 차트는 **최다인 날만** 값 표기 | 모든 점에 숫자를 붙이면 지저분해져 오히려 안 읽힌다 |
| 격자선은 옅게, 축 테두리 최소 | 눈이 데이터로 먼저 가게 한다 |

### 색을 쓴 원칙

| 차트 | 색 | 이유 |
|---|---|---|
| 카테고리 분포 | **한 가지 색** | 읽는 값은 길이 하나. 색이 다르면 "색깔별 뜻이 있나" 하고 읽게 된다 |
| 일자별 추이 | **한 가지 색** | 단일 계열 |
| 감성 분포 | **세 색** — 파랑/회색/주황 | 좋음↔나쁨 **양 끝이 있는 값**. 무지개색을 쓰면 어느 쪽이 나쁜 소식인지 읽을 수 없다 |

색이 뜻을 나르는 것은 감성 차트뿐이다. 나머지는 길이가 뜻을 나른다.

### 리포트 (요건 7)

| 요구 | 넣은 것 |
|---|---|
| 품질 지표 2개 이상 | **4개** |
| TOP N 집계 1개 이상 | **2개** (카테고리 TOP N, 최다 수집일) |
| AI 인사이트 | 저장된 분석을 인용 |
| 콘솔 + 파일 | 콘솔은 항상, 파일은 `--save --format md/txt` |

**실제 품질 지표**

| 지표 | 값 | 무엇을 알려주나 |
|---|---|---|
| 정제 통과율 | **10.6%** (16/151) | 수집 소스가 주제에 맞는가 |
| 요약 완료율 | **100%** (16/16) | AI 호출이 얼마나 실패했는가 |
| 본문 확보율 | **100%** (16/16) | 요약의 재료가 충실한가 |
| 크롤링 도달률 | **25.8%** (39/151) | 크롤링을 얼마나 돌렸는가 |

정제 통과율 10.6%는 낮은 것이 아니라 **필터가 제대로 일한다는 뜻**이다.
크롤링 도달률 25.8%는 `--target clean` 으로 **의도적으로 낮춘 값**이다.

그리고 이 지표들이 실제로 문제를 잡아냈다.
**본문 확보율이 낮았던 시점**에 요약이 "203자 → 148자"로 나왔고,
그 숫자를 보고 크롤링 범위를 넓혔다. 지표가 없었다면 넘어갔을 문제다.

### 내보내기 (요건 8 — 2개 이상 → 3개)

| 형식 | 특징 |
|---|---|
| CSV | `utf-8-sig`(BOM) — 없으면 **엑셀이 한글을 깨뜨려 연다** |
| JSONL | 한 줄에 기사 하나. 다른 프로그램이 이어받기 좋다 |
| Excel | 제목 줄 고정, 열별 자동 필터, 줄바꿈 서식, 열 너비 조정 |

필터: `--status all/summarized/unsummarized`, `--category`

> 📸 `17_charts.png` `18_report.png` `20_export.png` `23_sentiment_chart.png`

### 📋 요약

| 질문 | 답 |
|---|---|
| 집계는 어디서 하나? | SQL `GROUP BY` — 파이썬 반복문이 아니라 DB에 맡긴다 |
| 한글이 깨지는 이유는? | matplotlib 기본 폰트에 한글 글자가 없다 → 설치된 한글 폰트를 찾아 지정 |
| `unicode_minus` 는 왜? | 없으면 음수 눈금의 마이너스 기호가 깨진다 |
| 차트 색을 왜 하나만 썼나? | 읽는 값이 길이 하나뿐이라. 감성 차트만 색이 뜻을 나른다 |
| 품질 지표를 왜 넣나? | "몇 건 모았다"로는 파이프라인 건강을 알 수 없다. 실제로 203자 요약 문제를 이 지표로 잡았다 |
| CSV에 BOM을 왜 붙이나? | 없으면 엑셀이 cp949로 읽어 한글이 깨진다 |

## 7. 하지 않은 선택과 그 이유
